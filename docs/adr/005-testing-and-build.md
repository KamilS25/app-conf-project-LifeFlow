# ADR 005. Тестирование, миграции и публикация образа LifeFlow

## Статус

Предложено, 27.11.2026. Автор — Салахетдинов Камиль (`KamilS25`).

## Контекст

LifeFlow использует PostgreSQL 17, SQLAlchemy, Alembic и GitHub Flow. [ADR 004](004-ci-pipeline.md) добавил проверки кода и секретов. Для приёмки изменений нужны автоматические проверки миграций и API на PostgreSQL, покрытие кода приложения от 60% и сборка образа с привязкой к коммиту `main`. [Definition of Done курса](https://github.com/andrey-limasov/app-conf/blob/main/definition-of-done.md#4-cicd-пайплайн)

## Рассмотренные варианты

| Вариант | Преимущества | Ограничения |
| --- | --- | --- |
| Сервис-контейнер PostgreSQL в GitHub Actions | Чистая БД на каждый прогон, та же основная версия, что в Compose | Для локального полного прогона нужен Docker и настройка адреса тестовой БД |
| PostgreSQL через Testcontainers | Тесты сами управляют контейнером | Дополнительная зависимость и управление Docker из pytest |
| SQLite или подмена соединения | Быстрый старт тестов | Нельзя проверить PostgreSQL-миграции, ограничения и поведение запросов на рабочей СУБД |

## Решение и обоснование

1. `test` запускается в GitHub Actions с сервисом `postgres:17` и случайным портом. Шаг `Migrations` применяет `alembic upgrade head`. Интеграционные тесты получают адрес через `LIFEFLOW_TEST_DATABASE_URL`. Тесты, меняющие схему, создают уникальные схемы и удаляют их после прогона.
2. Источник схемы — миграции Alembic. Команда запуска контейнера применяет `alembic upgrade head` после проверки готовности PostgreSQL в Compose, затем запускает Uvicorn. В CI миграции проверяются отдельным шагом, а в тесте — применением на пустой схеме, чтением ревизии и повторным запуском.
3. `pytest-cov` считает покрытие Python-кода приложения (`app/`, `main.py`, `settings.py`). Отчёт показывает итог `TOTAL` и пропущенные строки. Тесты, исторические скрипты Alembic и виртуальное окружение исключены из измерения. Приёмка сверяет `TOTAL` с минимумом 60%.
4. `lint`, `secrets`, `test` и `build` запускаются параллельно для PR в `main` и push в `main`. Все четыре статуса обязательны для merge, а `publish` ждёт успеха всех четырёх джобов на push в `main`. `build` передаёт в `publish` уже собранный образ через артефакт. `publish` один получает право записи в Packages и отправляет этот образ в GHCR с тегом `sha-<полный SHA>` и OCI-метками источника и ревизии.
5. Локальное воспроизведение с PostgreSQL 17 и отчётом покрытия описано в [CONTRIBUTING.md](../../CONTRIBUTING.md#как-запустить-тесты-локально).

## Последствия и проверка

- Сбой обязательных тестов или сборки блокирует PR. Публикация использует образ того же прогона, который собрал `build`. Передача архива увеличивает время и расход хранилища на прогонах `main`. Срок хранения артефакта — семь дней.
- В локальном прогоне 16 тестов прошли на отдельном PostgreSQL 17. Итог `TOTAL`: 206 строк, 3 пропущены, покрытие 99%. На чистом томе Compose применил миграцию `0001`, `/health` вернул `200`. При повторном запуске задача осталась доступна.

## Приложение А. Тест-план

| Сценарий | Автоматическая проверка |
| --- | --- |
| `GET /`, JSON-ответ | `test_root_serves_json` |
| `GET /version`, версия и команда | `test_version_matches_project_metadata` |
| `GET /health`, БД доступна и недоступна | `test_health_checks_running_postgres`, `test_health_returns_503_when_postgres_is_unreachable` |
| `/docs` в `dev` и `prod` | `test_docs_availability_depends_on_environment` |
| Старт без `DATABASE_URL` или с недопустимым `APP_ENV` | `test_application_refuses_to_start_without_database_url`, `test_application_refuses_to_start_with_invalid_environment` |
| Alembic на чистой схеме и при повторном запуске | `test_alembic_upgrades_a_clean_schema_and_can_repeat` |
| Создание, чтение, изменение и удаление задачи, пагинация, валидация, изоляция и OpenAPI | `tests/test_tasks.py` |
