## Контекст

LifeFlow — учебный сервис на FastAPI для личных задач и целей. Канбан-доска, личные финансы и почтовые уведомления относятся к дальнейшему развитию продукта. В практике №2 обсуждаем процесс работы с Git и изменение `GET /version`, без внедрения этих функций и инфраструктуры.

Характеристики команды и проекта:

- Три участника с параллельными задачами: документация процесса, ADR и небольшой кодовый PR.
- Камиль уверенно работает с Git, у Елизаветы средний уровень, Виктория изучает Git.
- Демо проходят раз в две недели. Релизы выпускаются по готовности завершённых и проверенных этапов; автоматического деплоя после каждого merge пока нет.
- `main` должна оставаться стабильной: из неё запускают приложение и показывают результат преподавателю и другим командам.
- Уже используются FastAPI, `pyproject.toml` и `uv.lock`. Автоматические проверки CI не настроены; локальный запуск и review остаются необходимыми проверками.
- Репозиторий принадлежит личному аккаунту Камиля. Виктория имеет право записи, но не административный доступ.

Нужен понятный процесс параллельной работы, который ограничивает размер изменений и конфликты, сохраняет стабильную `main` и обеспечивает проверяемые PR с чужим approval согласно Definition of Done курса.

## Рассмотренные варианты

### Вариант A: GitFlow

**Суть:** постоянные ветки `main` и `develop`, рабочие ветки для функций, отдельные ветки подготовки релизов и срочных исправлений. Изменения требуется переносить между соответствующими линиями разработки.

**Плюсы:**

- Можно отдельно готовить следующий релиз и исправлять выпущенную версию.
- Явные этапы подготовки релиза помогают при поддержке нескольких версий продукта.

**Минусы:**

- Несколько постоянных и служебных веток усложняют обучение и выбор базы PR.
- Дополнительные слияния и переносы исправлений увеличивают затраты и риск расхождения веток.

**Подходит ли нам:** избыточно на текущем этапе. У трёх участников нет подтверждённой потребности одновременно поддерживать несколько выпущенных версий, а демо раз в две недели не требует отдельной постоянной `develop`.

### Вариант B: GitHub Flow

**Суть:** одна стабильная `main`; небольшое изменение выполняется в отдельной короткоживущей ветке от `main`, проверяется в PR и сливается обратно. Готовность merge и момент релиза могут различаться: в LifeFlow деплой после каждого merge не настроен.

**Плюсы:**

- Один цикл «ветка → PR → review → merge» понятен начинающему участнику и подходит для трёх параллельных задач.
- Одна постоянная ветка уменьшает затраты на синхронизацию, а PR и защита `main` дают видимую историю проверки.

**Минусы:**

- Ожидание review задерживает merge; при долгом ожидании рабочая ветка успевает отстать от `main`.
- Без автоматических тестов стабильность зависит от полноты ручных проверок; отдельной ветки интеграционного тестирования нет.

**Подходит ли нам:** да, при небольших PR, явных критериях approval и обязательном локальном запуске кодовых изменений.

### Вариант C: Trunk-Based Development

**Суть:** частая интеграция небольших изменений в общий trunk; рабочие ветки, если применяются, живут очень недолго. Для курса возможен вариант с PR и обязательным approval, без прямого push в защищённую ветку.

**Плюсы:**

- Частая интеграция уменьшает время расхождения веток и размер конфликтов.
- Маленькие изменения проще просматривать и быстрее связывать с причиной ошибки.

**Минусы:**

- Требует уверенного дробления работы, быстрой проверки и дисциплины команды с разным опытом Git.
- При отсутствии CI частая интеграция увеличивает нагрузку на ручные проверки; сокрытие незавершённых функций потребовало бы дополнительных приёмов.

**Подходит ли нам:** с оговорками, но сейчас менее удобен. Скорость review и автоматические проверки ещё не обеспечены, поэтому сначала осваиваем короткие ветки GitHub Flow с обязательным PR.

## Решение

Для LifeFlow выбрали **GitHub Flow**. Постоянная защищённая ветка — только `main`; `develop`, `release/*` и отдельный процесс GitFlow не вводятся.

### Схема ветвления

```text
main:                       A----------------------------------M---->
                             \                                /
feature/version-endpoint:     B----C----D---------------------/
                                      PR -> review -> approval

A — актуальная main, от которой создана рабочая ветка.
B–D — коммиты задачи и исправления после review в той же ветке.
M — merge-коммит PR в main после выполнения условий слияния.
```

Слияние `M` выполняется после review и approvals для последнего проверенного коммита. Релиз и демонстрация проверенного этапа планируются отдельно.

### Правила работы с ветками

1. Рабочая ветка создаётся от актуальной `origin/main` после `git fetch origin`. Локальная `main` обновляется через fast-forward при чистом рабочем дереве. Незакоммиченные изменения сохраняются.
2. Имя ветки имеет форму `<тип>/<краткое-название-в-kebab-case>`. Используем `feature/` для функций, `bugfix/` для ошибок, `docs/` для документации, `refactor/` для рефакторинга, `test/` для тестов и `chore/` для служебных изменений. Примеры: `feature/version-endpoint`, `bugfix/health-response`, `docs/adr-001-branching-strategy`, `chore/dependency-files`. Примеры показывают формат; не все такие ветки уже существуют.
3. Коммиты следуют Conventional Commits. Основные типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore` с кратким описанием. Реальные сообщения из истории: `docs: add reviewer checklist to CONTRIBUTING` и `feat: add version endpoint`.
4. Любые изменения, включая документацию, возвращаются в `main` только через PR. Автор заполняет описание и чек-лист по [шаблону PR](https://github.com/KamilS25/app-conf-project-LifeFlow/blob/main/.github/pull_request_template.md), указывает воспроизводимые проверки и результаты, назначает другого участника команды; в diff отсутствуют `.env`, ключи, окружения и личные инструкции.
5. Перед Approve ревьюер проверяет имя ветки, заполненность чек-листа автора, diff, коммиты и отсутствие секретов. При изменении кода или зависимостей запускает приложение и проверяет `/health` и изменённые маршруты. Для изменения только документации достаточно проверки документа. Для merge требуется минимум один действующий approval другого участника команды для актуального состояния PR. Самоодобрение исключено.
6. Первый ответ внутреннего ревьюера — в течение 24 часов. Автор отвечает на каждое замечание правкой либо обоснованием. После новых коммитов и разрешения конфликтов автор запрашивает повторное review; прежние approvals сбрасываются защитой.
7. Обсуждение закрывает участник, оставивший замечание, после проверки исправления. До merge все обязательные обсуждения закрыты. После двух безрезультатных кругов вопрос выносим на встречу команды; оставшееся разногласие с позициями сторон фиксируем в рисках ADR, а спор о соответствии DoD передаём преподавателю.
8. Конфликты разрешает автор в своей рабочей ветке через merge актуальной `origin/main`, сохраняя нужные изменения обеих сторон. После проверки результата он делает обычный push и повторно запрашивает review. Force-push в совместной работе не используем; в `main` он запрещён сервером.
9. PR сливаем обычным **Merge pull request** с созданием merge-коммита. Squash и rebase для `main` исключены текущим ruleset, хотя переключатели этих способов включены на уровне репозитория. После merge GitHub автоматически удаляет рабочую ветку.
10. В практике №2 ADR и кодовый PR проверяют участники LifeFlow. При замечаниях применяем цикл `Request changes → исправления → повторное ревью → Approve`.

Руководство курса предусматривает межкомандное ревью ADR и кодового PR. LifeFlow выбрала внутренний формат для этой практики. В отчёте указываем, кто фактически провёл ревью.

### Фактическая защита репозитория

Правила проверены чтением GitHub API **2026-11-10**. Они относятся к default-ветке `main`: ruleset [`protect-main`, ID 24886325](https://github.com/KamilS25/app-conf-project-LifeFlow/rules/24886325), состояние `active`, условие `~DEFAULT_BRANCH`. Список исключений подтверждён владельцем отдельно.

| Параметр | Проверенное состояние |
|---|---|
| Слияние только через PR | `pull_request` |
| Минимум чужих approvals | `required_approving_review_count = 1` |
| Сброс approvals новыми коммитами | `dismiss_stale_reviews_on_push = true` |
| Закрытие обсуждений | `required_review_thread_resolution = true` |
| Допустимый способ merge | `allowed_merge_methods = ["merge"]` |
| Запрет force-push | `non_fast_forward` |
| Запрет удаления | `deletion` |
| Исключения из защиты | `bypass_actors = []`, подтверждено владельцем 2026-11-09 |
| Обязательные CI checks | Правило `required_status_checks` отсутствует; CI ещё не настроен |
| Автоудаление слитых рабочих веток | Настройка репозитория `delete_branch_on_merge = true` |
| Обход защиты текущим аккаунтом | Для `vst-17`: `current_user_can_bypass = never` |

Список исключений пуст, в том числе для владельца. Камиль подтвердил `bypass_actors = []` по ответу API от 2026-11-09 во [внутреннем ревью](https://github.com/KamilS25/app-conf-project-LifeFlow/pull/9#discussion_r4515008061). Ответ API для аккаунта `vst-17` не показывает это поле, но подтверждает `current_user_can_bypass = never` для этого аккаунта.

По командному плану Камиль 2026-11-01 получил отказы обычного push и force-push, после которых `main` осталась на `664af89a658b8ad1cef75e2223213966ecddc550`. Этот SHA относится к проверке защиты от 2026-11-01. Повторные проверки отправкой в `main` не выполнялись; удаление default-ветки экспериментом не проверяется.

## Обоснование решения

1. **Размер команды:** три участника могут параллельно вести небольшие независимые PR, не обслуживая постоянную интеграционную ветку и несколько линий релизов.
2. **Частота релизов:** демо раз в две недели и релизы по готовности этапов совместимы со стабильной `main`; отсутствие автоматического деплоя не мешает применять цикл GitHub Flow.
3. **Опыт:** один понятный цикл снижает нагрузку на Викторию, изучающую Git, и на Елизавету со средним уровнем; Камиль может сосредоточиться на review и настройках вместо переносов между постоянными ветками.
4. **DoD и текущие ограничения:** PR с чужим approval и серверной защитой дают проверяемый процесс. Пока нет CI, локальный запуск и документирование результатов уменьшают риск регрессии, но не устраняют его полностью.

## Последствия

### Положительные (+)

- У всех изменений одна база и один путь проверки, включая документацию и конфигурацию.
- Небольшие PR позволяют проследить автора, обсуждение и проверки перед merge.
- Защита `main` делает обязательными PR, approval и разрешение обсуждений.

### Отрицательные (-)

- Ожидание участника с правом засчитываемого approval может задержать даже небольшой PR; новые коммиты требуют повторной проверки.
- Без CI ручной запуск увеличивает время review и не гарантирует обнаружение всех ошибок.
- Поддержка нескольких выпущенных версий не описана; при появлении такой потребности стратегию придётся пересмотреть отдельным ADR.

### Риски и митигация

| Риск | Вероятность | Влияние | Митигация |

| Единственный владелец — Камиль (`KamilS25`): без него настройки репозитория и защиты изменить нельзя | Средняя | Высокое | Выписать проверенный состав правил в ADR и `CONTRIBUTING.md`; изменения настроек планировать на встречах с владельцем. | Ошибка попадёт в стабильную `main` до появления CI | Средняя | Высокое | Ревьюеру запускать кодовый PR и проверять `/`, `/health`, изменённые маршруты и `/docs`; записывать ответы в PR. Обязательные CI checks вводить после появления CI отдельной согласованной задачей |
